# Telegram и нативный BB10-клиент

## Направление

Интерфейс — Cascades/QML и C++ с использованием системного Qt 4. Список и
переписка уже отделены от демонстрационных данных через `ChatController`.
Нативный UI должен учитывать квадратный экран, фокус, трекпад и физическую
клавиатуру Classic.

Предпочтительный результат — самостоятельный клиент: Telegram-движок и сессия
на телефоне. Удалённый шлюз не выбран в качестве архитектуры по умолчанию.

## Выбор Telegram-движка

[TDLib](https://core.telegram.org/tdlib) берёт на себя протокол, шифрование,
локальное хранение и получение обновлений. В актуальном
[репозитории TDLib](https://github.com/tdlib/td) указаны C++17, OpenSSL,
zlib, CMake и gperf. BB10 не указан среди основных целевых платформ.

Наличие C-интерфейса TDLib не означает, что готовая настольная библиотека
будет работать на QNX. Сначала требуется доказать сборку и работу зависимости
для обеих архитектур. При использовании более нового компилятора отдельно
проверить QNX ABI, C++ runtime и совместимость с библиотеками Qt 4/Cascades.
C ABI помогает ограничить интерфейс, но сам по себе эти проблемы не решает.

Первый технический эксперимент:

1. Зафиксировать ревизию TDLib и версии зависимостей.
2. Получить минимальную библиотеку для BB10 x86; проверить загрузку и JSON API
   без интерфейса приложения.
3. Повторить для BB10 ARMv7. Успех только в симуляторе ещё не доказывает
   работоспособность на Classic.
4. Проверить создание клиента, получение состояния авторизации и сетевое
   соединение. Затем подключать телефонный номер, код и двухэтапную проверку.

Перед самостоятельным портированием полезно найти поддерживаемые community
порты и воспроизводимые инструкции. Архивный
[arfeo/Telega](https://github.com/arfeo/Telega) показывает существовавший проект
для BB10, но его актуальность и возможность использовать его как основу пока
не подтверждены. Совпадение названия с современными сборками из каталогов
не доказывает, что это тот же проект. Код из него в этот репозиторий не скопирован.

Если актуальный движок не удастся перенести с приемлемыми затратами, можно
обсудить отдельный процесс или внешний шлюз. Последний добавляет зависимость
от сервера и меняет место хранения сессии; это отдельное продуктовое решение.

## Минимальная рабочая версия

- Вход в существующий аккаунт, включая код и пароль двухэтапной проверки.
- Список чатов и загрузка истории по мере прокрутки.
- Отправка и получение текста с настоящими состояниями доставки.
- Сохранение сессии и повторное подключение после потери сети.
- Читаемая раскладка Classic и навигация с физической клавиатуры.

После этого — медиа, файлы, поиск, уведомления и интеграция с Hub. Звонки
и секретные чаты не входят в первый этап.

## Граница с QML

Идентификаторы чатов, пользователей и сообщений передавать как строки,
чтобы избежать потери точности 64-битных чисел в JavaScript.
Изменять Cascades-модели в UI-потоке; события сетевого движка доставлять
через очереди сигналов/слотов. Не выполнять блокирующие сетевые вызовы
из обработчиков QML.

`sendDemoMessage` намеренно имеет отдельное имя: локальное добавление строки
не должно превращаться в ложное подтверждение отправки в Telegram.

## Доступ к API

Для собственного клиента нужны собственные `api_id` и `api_hash`:
[инструкция Telegram](https://core.telegram.org/api/obtaining_api_id).
Bot API не заменяет API пользовательского клиента.

Данные сессии и ключи не добавлять в git. Политику хранения сессии на BB10
нужно определить до реализации настоящей авторизации. На этапе каркаса
приложение не запрашивает данные аккаунта.
