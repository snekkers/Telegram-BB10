# Cascades и авторизация Telegram

30 октября 2026 добавлена связь между Qt 4/Cascades и отдельным процессом
TDLib. Разработка и сборка выполнены на Mac M1. Переход на Windows для
этого этапа не потребовался.

## Что добавлено

В главном экране есть действие «Вход в Telegram». Оно открывает нативную
страницу с запуском движка, его версией, состоянием и полями текущего шага.
Поддержаны API-параметры, номер существующего аккаунта, код, пароль
двухэтапной проверки, адрес почты и код из письма.

В 0.7.0 добавлен отдельный первый экран, автоматический локальный запуск движка
при открытии входа и свёрнутые настройки подключения. В debug можно явно
выбрать ограниченные официальные тестовые API-параметры Telegram Desktop;
в release этот путь отключён. Ключи не сохраняются и не выбираются автоматически.
[Новый интерфейс, ограничения и источники](interface.md).

Состояние меняется по `updateAuthorizationState`, а не по нажатию кнопки
или ответу `ok`. Пока ждём следующий шаг, повторная отправка отключена.
Запросы сопоставляются по `@extra`; запоздалый ответ старого шага игнорируется.
Регистрация нового аккаунта, покупки Premium, QR и восстановление пароля
не реализованы; неизвестный шаг отображается явно.

После `authorizationStateReady` показывается результат входа.
Начиная с 0.3.0 главный экран после входа показывает чаты Telegram,
историю и текстовую отправку. С 0.7.0 демо открывается отдельным выбором до входа.
[Реализация и проверки чатов](telegram-chats.md).

При запуске процесс получает только пути к бинарнику и библиотеке.
API-параметры и учётные данные идут через pipe, не через аргументы командной
строки. Стандартный вывод содержит JSON; диагностика не сохраняется.
Ошибки TDLib преобразуются в безопасные сообщения без вывода исходного JSON.
При остановке закрывается stdin: C-процесс запрашивает `close`, ждёт закрытия
TDLib и завершается. Принудительное завершение применяется после тайм-аута.
Остановка сохраняет сессию и не выполняет выход из аккаунта.

## Хранение

- В 0.4.0 `api_id` и `api_hash` можно сохранить явным выбором в форме входа.
  Файл `api.json` имеет права 0600 и содержит параметры без дополнительного
  шифрования. Для повторного запуска есть кнопка использования сохранённой пары.
  Получить их можно в [API development tools](https://core.telegram.org/api/obtaining_api_id).
- Коды и пароль не сохраняются; поля очищаются после отправки и смены шага.
- Данные TDLib находятся в `data/telegram` внутри sandbox приложения.
  Каталог имеет права 0700, файл `database.key` — 0600.
- Для ключа используются 32 байта из `/dev/urandom`, либо `/dev/random`
  на QNX. При отсутствии источника случайных байтов запуск базы отклоняется.
- Ключ передаётся в `database_encryption_key` как base64. Пустой, повреждённый
  или символьный файл ключа отклоняется. Если ключ исчез при наличии данных,
  новый не создаётся автоматически.
- Ключ лежит в том же sandbox: копирование всего каталога даёт и базу, и ключ.
  Аппаратное хранилище ключей не реализовано. Это шифрование базы, а не
  дополнительный пароль пользователя на доступ к ней.
- В 0.4.0 включён дисковый кеш сообщений TDLib. Секретные чаты отключены.

## Разделение библиотек

Device BAR содержит `telegram/bin/berrygram-tdjson`, `telegram/lib/libtdjson.so`,
`libstdc++.so.6`, `libgcc_s.so.1`, manifest и тексты лицензий.
Общий `LD_LIBRARY_PATH` приложения не включает этот каталог.
Только `QProcess` получает путь к библиотекам движка.
ELF интерфейса связан с системным `libcpp.so.4`; GNU runtime в него не включён.

Simulator BAR содержит экран входа и адаптер, но не содержит ARM-библиотек.
Кнопка запуска отключена с пояснением. Для полноценного теста Telegram
в x86-симуляторе ещё нужна отдельная сборка TDLib для x86.

## Проверки на M1

```sh
bash scripts/test-telegram-session.sh
bash scripts/build-docker.sh simulator
bash scripts/build-docker.sh device
python3 tests/verify-bars.py
```

Команда Device требует уже подготовленный
[ARM runtime](qnx-port.md). Скрипт упаковки сначала проверяет хеши.

Qt-тесты выполняются в Linux ARM64-контейнере с Qt 5.15.8, сеть во время
выполнения отключена. Тот же `TelegramSession.cpp` работает с тестовым
процессом и с настоящей TDLib 1.8.69 из закреплённого community wheel
[AYMENJD/tdjson](https://github.com/AYMENJD/tdjson). SHA-256:
`bbf04c8a9038f816bc52b2e34b1d8432e9797968dfb45244c0dacf0d88822530`.
Библиотека извлекается без установки Python-модуля и используется только
в Linux-тестах. В BB10 BAR её нет.

Прошли 13 сценариев (15 строк QtTest вместе с setup/cleanup): JSON/Unicode
и framing, телефон/код/пароль, почта, два неподдержанных шага, три отказа
процесса, повреждённый/потерянный/символьный ключ, отсутствие комплекта,
запуск настоящей TDLib без параметров, обработчик тайм-аута и отказ запуска.
Проверены повторный запуск, сохранение ключа, значимые пробелы в пароле,
запоздалые ответы, дубли состояния и пауза между `ok` и новым шагом.

С настоящей библиотекой выполнены только получение версии и начального
состояния, затем закрытие. Сессия, сетевое соединение и вход не создавались.

Отчёты: `build/session-tests/results.xml`, `results.qt.xml`,
`build/verification.json`. Обе BB10 цели компилируются штатным SDK с Qt 4
и C++98; Qt 5 нужен только для доступного на M1 тестового окружения.
В тестах используется Qt 5 JSON codec; BB10 использует `bb::data::JsonDataAccess`.
Его код компилируется, но выполнение на QNX ещё не проверено.

**Обновление 12 ноября:** установка development BAR на Classic, запуск UI,
QProcess/ARM TDLib, JSON с Unicode, источник энтропии, SHA-256 и создание TLS
context проверены отдельно на физическом SQC100-4. Пользователь подтвердил
версию TDLib в интерфейсе 0.6.1 и первый экран нового интерфейса 0.7.0.
Сетевой TLS, вход и настоящие чаты ещё не проверены. Рабочий графический
симулятор на M1 пока не получен. [Свидетельства на Classic](classic-device.md).

Поведение авторизации сверено с закреплённым `td_api.tl` из QNX-порта и
[официальным описанием TDLib](https://core.telegram.org/tdlib/getting-started).
