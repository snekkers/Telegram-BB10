# Telegram 0.16.1.22: возврат из фона и нагрузка процессора

## Найденные причины

В QNX-порте TDLib использовался backend `TD_POLL_POLL`. Его реализация продолжала
передавать в `poll()` интерес к записи даже после того, как флаг готовности уже
был доставлен обработчику. Подключённый сокет обычно готов к записи, поэтому
сетевой планировщик мог непрерывно просыпаться. В используемом TDLib backend
`Select` уже исключает такие ожидающие обработки флаги.

Отдельная проверка настоящего backend на Classic, без аккаунта и внешней сети,
воспроизвела проблему: повторное ожидание на 150 мс завершалось за 0 мс.
После исправления ожидание занимает около 151 мс. Чтение новых данных,
повторное ожидание после опустошения сокета, закрытие соединения и освобождение
подписок также проверены. Исправление находится в `porting/tdlib-qnx-poll.patch`;
оно применяется вместе с основным QNX-патчем при подготовке исходников.

В приложении также обнаружены пробелы восстановления после возврата:

- Изменения сети использовались только для автозагрузки вложений и не передавались
  в TDLib через `setNetworkType`. Этот метод [по документации TDLib](https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1set_network_type.html)
  переоткрывает соединения при смене сети, в том числе при смене сети того же типа.
- Возврат в приложение не заменял оставшийся без ответа запрос истории.
- Автоматическая подгрузка списков могла продолжаться при свёрнутом приложении.
- Поисковый таймер работал каждую секунду даже без поисковых запросов.

Непрерывная работа сетевого планировщика способна расходовать батарею и увеличивать
задержки. Это подтверждённая ошибка ожидания событий; точная причина каждого
пользовательского зависания в реальном аккаунте отдельно не установлена.

## Что изменено

- `poll()` ожидает только ещё не доставленные обработчику события; уже доставленные
  закрытие и ошибка исключаются до обработки. Исправлены освобождение подписок
  и удаление дескриптора без использования недействительного итератора.
- Смена сети передаётся движку. Повторные сведения о той же сети не вызывают
  переоткрытие соединений при каждом опросе; возврат из фона обновляет соединение.
- При возврате заменяются только незавершённые запросы чтения истории и списка чатов.
  Поздний ответ старого запроса не завершает новый запрос. Отправки, правки и
  пересылки не повторяются автоматически, черновики сохраняются.
- Для истории, списка чатов и обновления сети действует предел ожидания 15 секунд.
  При ошибке истории доступна кнопка «Повторить загрузку».
- Фоновые AutoPager, запуск новых загрузок аватаров, опрос типа сети для
  автозагрузки и таймер статусов останавливаются. Соединение для уведомлений,
  входящие события и уже выполняющиеся пользовательские операции сохраняются.
- Поисковый таймер включается только при наличии ожидающих запросов.
- Хэш исправления poll включён в manifest движка и проверяется перед упаковкой,
  чтобы в новую сборку случайно не попал прежний движок.

## Замер до исправления

16 ноября 2026 года на Classic SQC100-4 пользователь свернул приложение и оставил
телефон без действий. За интервал 62,5 секунды процесс TDLib использовал примерно
**63,3% одного ядра**, интерфейс — **23,3% одного ядра**. Это средние значения по
приращению пользовательского и системного процессорного времени `pidin times`,
а не проценты заряда батареи. Телефон был подключён по USB и заряжался.

Сравнение скорости разряда в процентах в час требует отдельного прогона без зарядки
при сопоставимых сети, яркости и состоянии экрана. Этот короткий замер не позволяет
оценить время автономной работы или подтвердить устранение всех зависаний
после длительной работы.

## Проверка после обновления

Telegram **0.16.1.22** установлен на тот же Classic с сохранением данных.
Хэши всех 94 файлов пакета проверены после установки. После первого запуска
пользователь увидел таймаут загрузки чатов; затем список загрузился.
Пользователь подтвердил загрузку сообщений в нескольких чатах после возврата
из свёрнутого состояния. Первоначальный таймаут не считается устранённым
во всех сетевых условиях.

Для сравнения нагрузки взяты последние примерно 31 секунды каждого минутного
замера, после начального перехода состояния. Значения — доля одного ядра:

| Процесс | До обновления | После обновления |
|---|---:|---:|
| TDLib | 59.04% | 0.10% |
| Интерфейс | 9.51% | 0.82% |

За полный интервал около 62 секунд средняя нагрузка движка снизилась с 63,32%
до 1,25%, интерфейса — с 23,25% до 12,21%. Начальная часть второго замера включает
переход к покою после загрузки чатов. Поэтому стабильные значения приведены отдельно,
а весь минутный интервал не представлен как установившийся режим.

Это подтверждает устранение измеренного фонового цикла, но не является замером
скорости разряда аккумулятора. Телефон продолжал заряжаться по USB.
Длительный сценарий с десятью минутами активной переписки и многократными возвратами
пока не проверен; короткий пользовательский цикл возврата прошёл успешно.

## Проверки

В Linux ARM64 / Qt 5 прошли 113 проверок, включая пять новых сценариев:
фоновая подгрузка, потерянный запрос при возврате, поздний ответ старого запроса,
смена сети без повторных переподключений и отсутствие повторной отправки сообщения.
Сохранены проверки неопределённых отправок, черновиков, вложений, комментариев,
реакций, поиска, аватаров и голоса.

Проверка QNX backend находится в `tests/qnx-poll-tests.cpp`.
После подготовки TDLib её можно собрать через
`bash scripts/build-qnx-poll-test.sh`; результат —
`build/porting/work/qnx-poll-tests`. Запускать на BB10 с библиотеками C++
из подготовленного комплекта `telegram-runtime/lib`.
