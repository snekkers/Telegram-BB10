# Telegram-движок: проверка без симулятора

29 октября 2026 на M1 выполнен первый тест с настоящей TDLib 1.8.69.
Он не требует BB10 GUI, Windows, `api_id`, номера телефона или входа в аккаунт.
Параметры TDLib и база сессии в этой проверке не создаются.

## Что реализовано

`engine/tdjson-host.c` — отдельный локальный процесс `berrygram-tdjson`.
Он загружает библиотеку TDLib через современный JSON C API:
`td_create_client_id`, `td_send`, `td_receive`, `td_execute`.

- stdin принимает по одному JSON-запросу в строке UTF-8.
- stdout содержит только JSON-ответы и обновления TDLib.
- stderr содержит ошибки процесса без печати запросов и ответов.
- EOF, SIGTERM и SIGINT запрашивают `close`; процесс ждёт
  `authorizationStateClosed` не более 10 секунд.
- При явном запросе `close` процесс также завершается после этого обновления.
- Размер входной строки ограничен 1 MiB; NUL внутри запроса отклоняется.
- Возвращённая TDLib строка обрабатывается до следующего receive/execute.

Это граница между Cascades и движком. Оба процесса должны работать
на самом телефоне; внешний сервер для этого решения не нужен.
Адаптер `TelegramSession` и экран входа реализованы, процесс и ARM-библиотеки
включены в Device BAR. Настоящие чаты ещё не реализованы.
[Проверки адаптера и ограничения](telegram-login.md).

**30 октября получена полная QNX ARMv7-библиотека TDLib 1.8.69** с OpenSSL 3.5.9
и zlib 1.3.2. Строгая линковка и проверка ELF/C API прошли; проверка исполнения
на телефоне пока не выполнена. Подготовлен комплект `build/device/telegram-runtime.zip`.
[Результат переноса и команды сборки](qnx-port.md).

## Что проверено

На macOS arm64 с настоящей TDLib прошли восемь сценариев интеграции:

1. Запуск, состояние `authorizationStateWaitTdlibParameters`, версия 1.8.69,
   сопоставление запросов по `@extra`, ответ на неизвестный метод,
   обработка кириллицы и эмодзи, разрыв UTF-8 между записями в pipe,
   CRLF и правильные смещения text entities в UTF-16.
2. EOF закрывает клиент, включая последнюю строку без перевода строки.
3. NUL отклоняется с последующим закрытием клиента.
4. Строка длиннее 1 MiB отклоняется с последующим закрытием клиента.
5. SIGTERM приводит к закрытию клиента.
6. Отсутствующая библиотека даёт диагностируемую ошибку.
7. Библиотека без нужных C-символов отклоняется.
8. Относительный путь к библиотеке отклоняется.

Слово `authorizationStateClosed` внутри обычного текста не считается
уведомлением о закрытии: тип обновления проверяется структурно через jsmn.

Отчёт: `build/telegram/macos/integration-results.json`.
Вход в Telegram, сетевое подключение и работа базы данных не проверялись.

Тот же C-исходник успешно скомпилирован и слинкован SDK для:

| Цель | Файл | Результат |
| --- | --- | --- |
| macOS M1 | `build/telegram/macos/berrygram-tdjson` | Mach-O arm64; интеграционные тесты прошли |
| BB10 Simulator | `build/telegram/simulator/berrygram-tdjson` | ELF x86, `/usr/lib/ldqnx.so.2`; запуск не проверен |
| BB10 Classic | `build/telegram/device/berrygram-tdjson` | ELF ARM EABI5, `/usr/lib/ldqnx.so.2`; запуск не проверен |

Оба QNX-файла требуют только `libc.so.3` до загрузки TDLib.
Эта таблица относится к сборке нашего процесса. Полная библиотека TDLib
отдельно собрана только для ARMv7; её исполнение на QNX пока не проверено.

## Повторить на M1

Из корня проекта:

```sh
python3 scripts/prepare-tdlib-macos.py
bash scripts/build-telegram-host.sh macos
python3 tests/telegram-host-integration.py
```

Для кросс-компиляции с запущенным Docker Desktop:

```sh
bash scripts/build-telegram-host.sh simulator
bash scripts/build-telegram-host.sh device
```

Mac-скрипт скачивает закреплённый wheel `tdjson` из PyPI и извлекает dylib,
не устанавливая Python-модуль. Поэтому версия Python ABI в имени wheel
не требуется для запуска C-процесса. Проверяется SHA-256:
`85772d8a34ac96c3925896af66514846a70208cd81e2eedac8baf290d28a9ee0`.
Источники и контрольная сумма записаны в `build/tdlib/macos/wheel-source.json`.

Это community-сборка [AYMENJD/tdjson](https://github.com/AYMENJD/tdjson),
а не официальный бинарный релиз Telegram. В ней есть macOS-библиотеки
OpenSSL 1.1. Они использованы только в локальном тесте без авторизации;
данный комплект не выбран для выпуска и не переносится в телефонный BAR.
Mach-O arm64 также не подходит вместо QNX ARMv7 ELF.

## Что требуется для QNX

[Актуальная TDLib](https://github.com/tdlib/td) требует C++17.
Проверенная ревизия исходников upstream:
`4c6377aa7386c39217878a9a56d581922ad37ca4` от 27 октября 2026.
Из этой ревизии с локальным QNX-патчем теперь собрана ARMv7-библиотека.
Версия Mac-бинарника проверена через сам API;
точное соответствие бинарника этой upstream-ревизии не установлено.

Штатный GCC 4.6.3 в нашем BB10 SDK отклоняет `-std=c++17` для x86 и ARMv7.
Логи: `build/telegram/toolchain/*-cxx17.log`.
Смена компьютера на Windows этот предел версии SDK не меняет.

Есть [community builder GCC 9.3 для BB10](https://github.com/extrowerk/bb10-gcc9),
ревизия `4e163669c021dba5bfae88cb7fa1f5c97dca5e8c`.
В нём описан ARM toolchain и несовместимость C++ runtime с Cascades.
Сам builder с нуля не собирался. Использован готовый GCC 9.3.0 из BerryCore:
он проверен сборкой и линковкой C++17-программы. Для основного кода применяется
нативный Clang на M1 с GNU headers/runtime и GNU QNX linker.
Отдельный процесс позволяет не смешивать C++ runtimes в UI-процессе;
корректность работы полученной QNX-библиотеки ещё надо проверить на устройстве.

Следующие проверки — запуск диагностического комплекта на ARM-устройстве,
загрузка и закрытие клиента, файловые операции и сеть. Затем проверяется
вход через уже добавленный интерфейс. Для x86-симулятора нужен отдельный порт библиотеки;
готовая ARMv7-библиотека для него не подходит.

Документация протокола взаимодействия с TDLib:
[JSON C interface](https://core.telegram.org/tdlib/docs/td__json__client_8h.html).
